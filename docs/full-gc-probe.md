# Explicit full-GC probes

This isolated diagnostic measures the duration of **one explicit generation-2
collection after a preparatory full collection**. It separates the cost of that
call from the number of automatic collections observed in the previous workload.
It does not measure `loads()` latency and does not modify production cache code.

## Matched inputs and processes

Use a completed [pytest plugin profile](pytest-plugin-profile.md) report directory
as the reference. The runner validates its manifest, reports and payload hashes
before copying the existing payload bundle. It never exports a new payload from
the database. Only the `without_instance` control is restored: the same model
fields, loaded tags and removed instance hints are checked without SQL.

The two profiles are `autoload` and `django_only`. Both use the same installed
packages and `pytest.plugin-profile.ini`; the latter disables third-party
autoload and explicitly enables pytest-django. Built-in pytest plugins remain.
Registrations are checked before and after each worker. The original Python,
package versions, previous experiment sources, GC policy, hash seed and Django
configuration must match the reference. An incompatible reference is rejected.

The default matrix contains **16 fresh sequential processes**:
two validation modes × two profiles × four repeats. Each matched pair runs
adjacently; order alternates AB/BA by repeat. Validation modes stay separate in
the summary. Rows and warmup count are inherited. The reference's old operation
count is retained as metadata, but the 400-operation latency loop is not run.
Each new worker produces exactly one measured collection.

## Worker sequence

1. Verify plugins, runtime and payload. Restore and validate the control once
   during preflight; release that result before returning from preflight.
2. Run the same warmup schedule: one always-validated restore, then the inherited
   number of warmups, with optional validation. Delete every result. Return
   from the warmup function so that its temporary locals also go out of scope.
3. Preallocate primitive observation buffers. Require enabled GC, no external
   GC callbacks and one Python thread. Suspend automatic GC for the two explicit
   calls below, without changing thresholds, debug flags or the frozen set.
4. Call `gc.collect(2)` once for preparation, outside the measured interval.
5. Save GC state, measure the next `gc.collect(2)` with `perf_counter_ns`, then
   save GC state again. There is no serializer call, phase wrapper, GC callback,
   object inventory or weak-reference inspection in this measured interval.
6. Restore automatic GC in `finally`, including when a collection raises.
   Build the JSON report after the measurement. SQL is forbidden throughout
   payload restoration, validation, warmup and the probe.

Automatic GC operates normally during startup, preflight and warmup. Temporarily
suspending it for the explicit pair prevents an intervening automatic collection
from replacing the intended experiment. This is a diagnostic policy, not a
recommendation to disable GC in the application.

The timing interval includes the explicit call and timer overhead. Primitive
state buffers exist before preparation; temporary lists/dicts returned by
`gc.get_stats()` are released before timing starts. State capture still performs
some allocation outside the timer. Plugin checks, observers and this harness
also contribute live objects. Both profiles share the protocol, but their
heaps are not asserted to be identical. Do not treat old automatic pause times
and this new diagnostic as measurements of exactly the same heap.

## Running

Run from the repository root, with no concurrent benchmark, coverage, tracing,
profiling or tracemalloc. PostgreSQL, Redis and Memcached do not need to be
running: existing trusted payloads are reused and SQL is rejected. Only use
payloads generated by your own experiment; these files contain Python pickle.

```bash
set -o pipefail
reference_dir="$HOME/nova-reports/pytest-plugins-20261025-050322"
report_dir="$HOME/nova-reports/full-gc-$(date +%Y%m%d-%H%M%S)"

uv run --locked python scripts/run_full_gc_probe.py \
  --reference-dir "$reference_dir" \
  --output-dir "$report_dir" --repeats 4 \
&& uv run --locked python scripts/summarize_full_gc_probe.py \
  "$report_dir" --json "$report_dir/analysis.json" \
  | tee "$report_dir/analysis.txt"
```

The reference must contain the complete plugin-profile matrix and payloads,
not just `analysis.json`. Set `reference_dir` to its actual location if moved.
The runner refuses to overwrite an existing output directory. On failure,
`manifest.json` remains incomplete and identifies the failing worker's log.
The offline analyzer reads JSON and hashes payload bytes; it never unpickles.

## Reading the results

Every worker preserves both collection return values, measured start/end times,
and five GC checkpoints: before suspension, before preparation, before and after
the measured call, and after restoration. Each checkpoint contains enabled
state, thresholds, debug flags, frozen count, allocation counts, cumulative
generation statistics and callback count. Prefix events retain preflight/warmup
collections separately. There are no collection callbacks in the explicit pair.

The analyzer checks exactly one gen-2 collection in each explicit phase, no
extra collections at the boundaries, unchanged thresholds and successful
restoration. It reconciles each return value with the change in collected and
uncollectable counters, and checks sources, environment, plugins, work counts,
payload hashes, worker order and distinct process IDs.

Compare `elapsed_ms` within adjacent pairs. `django_only_over_autoload` below
one means the explicit call was shorter in that pair. `empty_pair_ratio` is
present only when **both calls returned zero**. Nonzero results are retained,
not silently discarded or made into failed runs; their durations appear in the
separate `nonempty` bucket. All/empty/nonempty summaries report sample size,
mean, median, minimum and maximum. Four samples per profile and validation mode
are descriptive; they do not support precise tail percentiles or confidence
claims.

A preparatory collection changes the heap and clears some interpreter free
lists. The next collection therefore estimates a particular post-preparation
state. If durations are similar while the previous automatic counts differ,
the evidence points toward frequency as the next question for that workload.
If durations differ, the live graph and its traversal remain candidates. Neither
outcome alone identifies a particular plugin, proves a leak or predicts
production request latency. This experiment intentionally does not test
automatic triggering or change its thresholds.
