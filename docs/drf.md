# Django REST Framework adapter

Install the `drf` extra and initialize Django before importing application
models. `to_drf_serializer()` returns a DRF `ModelSerializer` subclass for a
`NovaModel` with an explicit Pydantic schema in `_nova_config`.

```python
from decimal import Decimal
from typing import Literal

from django.db import models
from pydantic import BaseModel, Field

from nova import NovaConfig, NovaModel
from nova.ecosystem import to_drf_serializer


class InvoiceSchema(BaseModel):
    title: str = Field(min_length=3)
    amount: Decimal = Field(gt=0)
    currency: Literal["USD", "EUR"]


class Invoice(NovaModel):
    title = models.CharField(max_length=80)
    amount = models.DecimalField(max_digits=8, decimal_places=2)
    currency = models.CharField(max_length=3, default="USD")

    _nova_config = NovaConfig(pydantic_schema=InvoiceSchema)


InvoiceSerializer = to_drf_serializer(Invoice)
```

Define the model in an installed Django application and apply its migration.
Then use the serializer directly or assign it as a viewset's `serializer_class`:

```python
serializer = InvoiceSerializer(data={"title": "Invoice", "amount": "12.50"})
serializer.is_valid(raise_exception=True)
invoice = serializer.save()

patch = InvoiceSerializer(invoice, data={"amount": "20.00"}, partial=True)
patch.is_valid(raise_exception=True)
invoice = patch.save()
```

## Validation and persistence

DRF supplies transport fields, conversion, required/read-only behavior, choices,
and its normal model-derived validators. Nova then validates the complete
candidate state through Pydantic. Calling `is_valid()` does not save a row;
validation can read the database for uniqueness checks and relationship lookup.

`save()` still calls the model's authoritative validation lifecycle. Django
`Model.clean()`, uniqueness, and constraints remain active. Overrides supplied
through `serializer.save(**kwargs)` also reach that lifecycle. A rejected save
does not persist the tested invalid row, although DRF's update implementation may
already have assigned values to the in-memory instance.

Pydantic errors are translated into DRF `ValidationError` details. Model-level
errors use `REST_FRAMEWORK["NON_FIELD_ERRORS_KEY"]`, or `non_field_errors` by
default. Nested Pydantic error locations are grouped under their top-level field.
`is_valid(raise_exception=True)` supports normal DRF 400 responses.

An ORM `NovaValidationError` raised later by `save()` is not automatically
translated into a DRF exception. Applications must choose how to expose these
save-time errors. Database exceptions and errors in custom hooks likewise retain
their normal handling requirements.

The adapter validates Pydantic transformations but does not automatically write
the transformed Pydantic model back to Django. Persisted values follow DRF
conversion and the [Nova/Django validation lifecycle](validation.md). This is
distinct from adapting files and foreign keys for validation.

## Fields, defaults, and updates

| Case | Behavior |
| --- | --- |
| Field projection | Schema field names that exist on the model, plus the model primary key. Persistence-only fields are not exposed. |
| Read-only fields | Keep DRF's handling of generated IDs, non-editable fields, and generated timestamps; client values are ignored. |
| Required fields | Keep the required transport fields generated by DRF. Pydantic still validates the resulting complete object. |
| Scalar Django defaults on creation | For omitted projected fields with a Django default, evaluate the default during validation and retain that value for save. Callable defaults run once per validated item. |
| Omitted fields on update | Use the current instance for Pydantic cross-field checks. Do not evaluate creation defaults or add omitted fields to the write attributes. |
| `partial=True` | Permit omitted transport fields; supplied invalid values still fail. |
| Nullable/blank fields | Follow DRF/Django field settings and the canonical Pydantic schema. |
| JSON | Keep DRF JSON input and response behavior, with Pydantic validation of the selected schema type. |

Full updates still require DRF-required transport fields. The complete-state
validation payload does not turn an incomplete full update into a PATCH.

A partial update can repair an invalid existing value: if the current model
cannot be converted to a valid Pydantic instance, Nova reconstructs its canonical
dictionary, overlays the supplied attributes, and validates the merged state.
It does not suppress validation of invalid values left unrepaired.

Creation defaults are taken from Django persistence fields. Pydantic-only
defaults are not automatically turned into saved model attributes. Server-side
defaults may appear in `validated_data`, including defaults for projected
read-only fields; client input cannot override those read-only fields.

## Foreign keys and uploaded files

DRF still accepts references to existing related objects. If the schema expects
a scalar foreign-key value, the validation payload uses the referenced Django
field value, including `ForeignKey(to_field=...)`. The original Django instance
remains in `validated_data` for assignment during save.

For a nested or optional nested Pydantic schema, validation uses the resolved
related object. This does not generate a nested DRF serializer: the API input and
output retain DRF's reference representation. Nullable foreign keys can be
cleared with `null` when both model and schema permit it.

An uploaded file is represented by its name only in the Pydantic validation
payload. `validated_data` retains the original uploaded file, including its
contents, for Django storage. Storage can alter the final name; applications
remain responsible for their storage configuration and upload policy.

## Boundaries

- Automatic writable nested objects, many-to-many write semantics, relationship
  defaults, and arbitrary serializer `source` remapping need an explicit
  application serializer and their own tests. A projected field name alone does
  not establish those persistence contracts.
- `many=True` uses DRF's list serializer. Invalid input items are detected before
  list persistence, but a later save-time failure does not make the entire batch
  atomic. Use an application transaction for that requirement.
- This adapter does not add database locking between `is_valid()` and `save()`.
  Concurrent writes still require appropriate application/DB constraints.

## Verification

```bash
uv sync --locked --all-extras --dev
uv run --locked pytest -q \
  tests/ecosystem/test_drf_runtime.py \
  tests/ecosystem/test_drf_boundaries.py \
  tests/ecosystem/test_drf_integration.py \
  tests/query/test_drf_compiler.py \
  --cov=nova.ecosystem.drf --cov-branch \
  --cov-report=term-missing --cov-fail-under=85
```

The runtime tests perform real ORM writes and can run with either the default
SQLite settings or `--ds=tests.example_project.settings_postgres`. They also
exercise generated serializers through DRF viewset create and partial-update
actions. Type checking now includes the adapter in both repository Pyright
configurations.
