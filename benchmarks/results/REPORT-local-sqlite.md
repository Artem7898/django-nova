# Локальные измерения QuerySetCache

Источник: `cache-cost-local-sqlite.json`. 36 сочетаний backend/размера/сценария, по 5 операций — 180 серий. В каждой серии 3 прогрева, 25 замеров времени и 3 отдельных прохода tracemalloc. Проверки данных, независимости объектов и количества SQL прошли; запуск завершился с `1 passed`.

Среда: Python 3.12.14, Django 5.2.16, файловая SQLite 3.53.1, реальные Redis 7.4.2 и Memcached 1.6.39 на localhost. Клиенты: redis-py 8.1.0, pymemcache 4.0.0. Это отдельная проверочная среда, а не пользовательский PostgreSQL.

## Оценка

Создание снимка занимает заметную часть времени для 100 строк, особенно при prefetch_related. Измеряемый снимок проходит тот же `snapshot_rows`, что используется в QuerySetCache. В коде remote backend сначала восстанавливает результат из pickle, после чего QuerySetCache выполняет ещё один цикл сериализации и восстановления. Это конкретный кандидат для последующей оптимизации, если backend гарантирует независимые возвращаемые значения. Убирать защиту для backend, хранящего ссылки, нельзя.

В большинстве локальных случаев cache hit оказался медленнее прямого ORM-запроса. Здесь SQLite работает с небольшим прогретым набором данных; результаты не доказывают такое же соотношение для PostgreSQL, дорогих запросов или другой сетевой задержки.

Время `backend_get` показывает компонентную стоимость: оно не включает построение ключа, проверку поколений и снимок QuerySetCache. Показатели разных операций нельзя механически складывать или вычитать: они измерены раздельно, имеют разные входные состояния и подвержены шуму.

Данные относятся к одному запуску без конкурентной нагрузки на кэш. `sample_p95_ms` — квантиль небольшого набора лабораторных измерений, не production p95. Память отражает Python-аллокации внутри одного вызова, а не RSS или память серверов. Освобождение возвращённого результата не входит в измеряемое время вызова.

Полные данные для 1, 10 и 100 строк, CPU-время, сырые отсчёты и хэши исходников сохранены в JSON; сводка всех серий — в CSV.
